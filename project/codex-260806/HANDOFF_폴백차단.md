## 만들어진 구조 (7개 계산기 공통)

각 계산기에 모듈 스코프 순수 함수가 하나씩 있다 —
`acqFallbackGaps` / `inhFallbackGaps` / `giftFallbackGaps` / `propFallbackGaps` / `cgtFallbackGaps`.
전부 `(answers, calc) → 차단사유 문자열 배열` 이고, **두 층**으로 되어 있다.

| 층 | 무엇 | 엔진이 살아 있어도 막나 |
|---|---|---|
| ① 불확정·미지원 입력 | 사용자가 「모른다」고 했거나, 엔진이 그 사실을 받지 않는 것 | **막는다** |
| ② 폴백 한계 | 간이 계산만 못 푸는 것 (엔진은 제대로 푼다) | 막지 않는다 |

이 함수는 **두 곳에서 같이 쓰인다** — 규칙이 두 벌이 되면 반드시 어긋나기 때문이다.
1. `runAnalysis()` 안, **AI 프롬프트를 만들기 전** → 차단이면 즉시 `return`
2. 렌더 시작부 → 차단이면 결과 JSX를 **아예 만들지 않고** 조기 반환

## 왜 이 구조가 됐나 (되돌리지 말 것)

세 번 새고 세 번 고쳤다. 각 단계는 앞 단계로는 못 막는 누설이었다.

1. **헤드라인만 가림** → 계산표·카카오 버튼에 금액이 그대로 남았다
2. **조기 반환(렌더)** → 그보다 먼저 `window.claude.complete` 가 폴백 세액을 외부로 보냈다
3. **AI 호출 전 게이트** → 엔진이 «성공»하면 차단이 통째로 풀렸다. 그런데 엔진은
   모르는 필드를 조용히 유리한 쪽으로 가정한다 → ①층 신설

## 나머지 계산기 점검 결과 (260806 — 손댈 것 없음으로 판단)

차단 장치를 안 넣은 계산기들에도 같은 «엔진이 조용히 가정하는 필드»가 있는지 봤다.
**성격이 다르다** — 취득·양도는 「모른다」고 **물어봐 놓고 그 답을 버린** 것이고,

| 계산기 | 확인한 것 | 판단 |
|---|---|---|
| 종부세 | 나이·보유 미입력 → 288만 / 65세·10년 → 86.4만 (3.3배). 지분 미입력 → 50% 가정 (30%면 159.3만 vs 65.5만) | **차단 불요** — 문항에 「비워두면 50%로 봅니다」 명시, 나이·보유는 화면이 "넣어서 정확히" 안내. 방향도 과대 |
| 부가세 | `simplifiedSector`·`priorSupplyOver10` 둘 다 「모름」 선지 없고 필수 문항 | **문제 없음** |
| 소득세 | 미반영 항목을 자유서술로 받고 "본 계산에 미반영 — 상담에서 반영" 명시 | **차단 불요** |
