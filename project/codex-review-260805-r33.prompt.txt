전수 대조한 결과 **코드에 통째로 빠져 있던 조항 1건**을 찾았다.

## 찾은 것 — 종부세 「과세대상 문턱」(종부세법 §7① 신설)
1차 소스 (내가 PDF 에서 직접 추출한 원문):
- **상세본 p60** 「(2) 주택분 종합부동산세 과세대상 조정(종부법 §7①) … <신설> ➊(1세대1주택자)
  주택가액(공시가격) 합계액 **14억원 초과** ➋(➊외) 주택가액(공시가격) 합계액 **9억원 초과**
  … <적용시기> '27.1.1. 이후 납세의무가 성립하는 분부터 적용」
- **문답 p39** 「1세대1주택자는 보유주택 공시가격 합계액이 14억원 초과시 **과세대상**으로 하되,
  거주하는 경우 기본공제금액을 12→14억원으로 인상, 거주하지 않는 경우 12→9억원으로 인하」
- **개조식 p18** 도 같은 취지.

→ 즉 **기본공제와 «별개»의 선행 단계**다. 종전 코드엔 이 단계가 아예 없어 «없는 세금»을 만들었다:
- 비거주 1주택 13억 → 기본공제 9억만 적용해 과세. 실제는 14억 이하라 **0원**
- 2주택 합계 8억(비거주) → 공제 4억만 적용해 과세. 실제는 9억 이하라 **0원**

## 반영 내용
1. SSOT 에 `cre.taxableThreshold` 신설 (2026: null / 2027·2028: one 14억, multi 9억).
   2026 은 조항이 없지만 기본공제 12억·9억이 같은 일을 하므로 null.
2. `rfCalcCRE` 진입부에 「0. 과세대상 판정」 단계 추가 — 문턱 이하면 `notTaxable: true` 와
   사유 step 을 담아 즉시 반환(세액 0).
3. 비교표에서 `notTaxable` 인 해는 공제·과표·산출세액을 숫자 대신 「과세대상 아님 (N억원 이하)」·「—」로 표시
   (0원으로 찍으면 「공제가 사라졌다」로 읽힌다).
4. 「한 줄 결론」이 전 연도 0원이면 문턱 미달을 설명하고, 모순되는 「공제가 줄어 세금이 늘었다」 문구를 억제.
5. 부부 공동명의 고지를 문답 p40 실수치로 구체화(특례 신청 시 14억/9억, 개별 납부 시 각 9억/4억).
6. SSOT `source` 를 실제 대조 범위로 갱신 + 대조로 확인/발견한 것을 주석에 기록.
7. 회귀 CASE 20(문턱 8항)·CASE 21(문답 p40 적용사례 3항) 추가.

## 실측 (Claude 실행 — 당신 환경엔 node 가 없다)
- 비거주 1주택 13억·2027 → 0원 / 14억 정확히 → 0원 / 16억 → 3,396,000원
- 2주택 8억·2027 → 0원 / 9억 정확히 → 0원
- **문답 p40 적용사례와 공제액 일치**: 2주택 10억×2 1채거주 → 6.5억 · 비거주 → 4억 · 3주택 10억×3 1채거주 → 약 5.67억
- `npm run gate` 전 항목 통과. 브라우저 실동작 확인.

## 무엇을 볼 것
- 이 문턱 해석이 **원문과 맞는가**. 특히 ①「1세대1주택자」 문턱 14억이 «거주 여부와 무관»한 것이 맞는지
  (기본공제는 거주 14억/비거주 9억으로 갈리지만 문턱은 하나인지) ②「초과」이므로 정확히 14억·9억은
  과세대상이 아닌 것이 맞는지 ③2026년에 이 문턱을 두지 않은 것이 맞는지.
- 조기 반환이 만드는 새 결함 — 반환 객체 모양이 화면과 호환되는가, `notTaxable` 를 안 보는 표시 경로가 남았는가.
- 원문 대조로 «더 빠진 것»이 있는가. 저장소에 PDF 는 없지만 위에 인용한 원문과 코드 SSOT
  (`window.JT_REFORM_2026`)를 대조해, 내가 놓친 항목이 있으면 지적하라.
- R23~R32 반영분 회귀.
